## 关键结论：Dify 没有 E2E 测试

通读 `api/tests/` 后核心结论：

**Dify 的测试金字塔仅有两层**：
1. **Unit tests**（`api/tests/unit_tests/`）— 纯函数 / 类隔离测试
2. **Integration tests**（`api/tests/test_containers_integration_tests/`）— testcontainers Postgres + Redis 真实跑

**没有第三层 E2E**：
- 无 Playwright / Cypress / Selenium spec
- 无 web/ 前端 + api/ 后端的端到端打通
- 无浏览器视角的 button click → API → DB → email 全链路验证

**这与 CLAUDE.md §2.2 「E2E 是第一公民」原则相反 — 因此 Plan 04-12 不能从 Dify 借鉴 E2E 模式，只能借鉴集成测试的真实容器 + 状态机断言模式**。

## Dify 集成测试模式（可借鉴部分）

阅读 `api/tests/test_containers_integration_tests/tasks/test_mail_account_deletion_task.py`：

### 模式 1：testcontainers + 真实 DB session

```python
def test_send_deletion_success_task_success(
    self, db_session_with_containers: Session, mock_external_service_dependencies
):
    """fixture 注入真实 Postgres session + 部分外部依赖 mock"""
    account = self._create_test_account(db_session_with_containers)
    # 真实 DB 写入 + 真实邮件 task 入队
    send_deletion_success_task.run(account.email)
    # 断言 mock_mail.send 被调用 1 次
```

**借鉴**：
- 真实 DB（不 mock）— 我们的 conftest.py 已遵循
- 外部依赖（邮件 / IM）mock 出参数捕获 — 我们的 MockIMProvider 对应
- helper 方法 `_create_test_account` 抽离数据准备 — 我们的 `helpers/api_client.py`

### 模式 2：fixture mock external services + spec 验证 mock.calls

```python
@pytest.fixture
def mock_external_service_dependencies(self):
    with patch("tasks.mail_account_deletion_task.mail", autospec=True) as mock_mail:
        mock_mail.is_inited.return_value = True
        yield {"mail": mock_mail}
```

**借鉴**：
- 我们的 `mock_im_providers` autouse fixture 在测试 session 启动时替换真实 provider
- spec 内通过 `mock.calls` 列表断言（Dify 用 `mock_mail.send.assert_called_once()`，我们用 `mock.calls[0].method == 'send_hitl_card'`）

### 模式 3：subject / button 文案直接断言

Dify `test_mail_human_input_delivery_task.py`（如存在）走的也是 send → 断言 send call 参数包含正确的 button / link，**不点真实链接验证后端反应**。

**我们的扩展**：Plan 04-12 比 Dify 进一步 — 不仅断言 send 调用，**点 deeplink 真访问后端**验证：
- bot UA → 200 + jti 未消费（Safe Links）
- 真实 UA → 200 + 渲染决策页
- POST action → 309/200 + jti 消费 + sibling 失效

## 我们 Playwright E2E（浏览器视角）vs Dify pytest 集成（API 视角）

| 维度 | Dify 集成测试 | 我们 Plan 04-12 E2E（browser-harness + pytest） |
| ---- | ---- | ---- |
| 启动栈 | testcontainers Postgres + Redis | docker-compose 全栈（Postgres + Redis + MailHog + FastAPI + Nginx） |
| 浏览器 | 无 | browser-harness Chrome（仅 #5/#6 spec） |
| 测试视角 | API 调用 + ORM 查询 | API + ORM + UI 点击 + mailhog HTML 解析 + bot UA |
| 邮件验证 | mock send call 参数 | 真发 SMTP → mailhog 抓 → 解析 deeplink |
| Token 流 | 自构造 JWT 注入 | 真启动实例 → 等邮件 → 提取 token → POST |
| Safe Links | 无（Dify 无 bot 防护 — Pitfall 3 是我们独有强化） | 必含（CLAUDE.md §2.5 P0） |

## Safe Links bot regression 模式（Phase 3 已落，Plan 04-12 扩展到 chain）

**Phase 3 模式**（`e2e/hitl_safe_links_bot.spec.ts`）：
```typescript
const BOT_UAS = [
  'Mozilla/5.0 (compatible; Microsoft-Outlook-AC-Detector-Tool/1.0)',
  'Mozilla/5.0 SafeLinksScanner/1.0',
  'Mozilla/5.0 (compatible; Slackbot-LinkExpanding 1.0)',
  'Mozilla/5.0 (compatible; Googlebot/2.1)',
];

for (const ua of BOT_UAS) {
  test(`bot ${ua} GET 不消费 jti`, async ({ request }) => {
    const resp = await request.get(deeplinkUrl, {
      headers: { 'User-Agent': ua },
    });
    expect(resp.status()).toBe(200);
    // 用真实用户随后 GET 后 POST 成功 → 反证 jti 未被 bot 消费
  });
}
```

**Plan 04-12 扩展到 3 chain mode**：每个 chain spec 末尾 parametrize 跑 4 bot UA：
- `test_04_chain_sequential.py` → 顺序会签 + 4 bot UA Safe Links
- `test_04_chain_parallel_all.py` → 并行全员 + 4 bot UA Safe Links
- `test_04_chain_parallel_any.py` → 或签 + 4 bot UA Safe Links

**为何要在 chain mode 重复？**
- chain mode 涉及多 token 同时活跃 — bot 扫一封邮件不能影响其他 actor 的 token
- 防 regression：未来若有 chain-level invalidate 逻辑改动，bot 扫描可能误触

## 可借鉴的 Dify 模式（用于 Plan 04-12 spec 内）

| 模式 | 来源 | 应用 |
| ---- | ---- | ---- |
| `_create_test_X` 数据准备 helper | Dify 集成测试 | `helpers/api_client.py` 提供 `create_test_workspace_with_users(n=3)` |
| autouse fixture mock external | Dify | `conftest.py` `mock_im_providers` autouse session-scoped |
