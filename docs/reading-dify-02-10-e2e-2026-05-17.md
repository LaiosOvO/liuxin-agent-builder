## 项目概述（一句话）

Dify 的 E2E 测试用 Cucumber + Playwright 双层架构，BDD feature 文件描述场景，step-definitions 调 Playwright Page API，fixtures 提供预认证浏览器上下文，support/api.ts 提供 HTTP fixture 快速准备测试数据（绕过 UI）。

## 技术栈（关键技术选择）

- **测试框架**: `@cucumber/cucumber` BDD 层 + `@playwright/test` 作为 browser API
- **场景组织**: `e2e/features/**/*.feature` 按功能分 smoke/apps/auth 目录
- **Step definitions**: `e2e/features/step-definitions/` 对应 feature 分类
- **World 对象**: `DifyWorld extends World` — 每个 scenario 一个实例，携带 `context/page/createdAppIds` 等状态
- **测试数据 API**: `support/api.ts` — `createTestApp` / `syncRunnableWorkflowDraft` / `deleteTestApp` 直接调后端 API 建数据（比 UI 快 10x+）
- **认证 fixture**: `fixtures/auth.ts` — `authStatePath` 预存登录 cookie，注入到 `browser.newContext({ storageState })`
- **测试分级**: 通过 Cucumber tag 标注（`@smoke @authenticated @core @mode-matrix`）分级触发

## 架构要点（核心架构模式）

```
e2e/
├── features/
│   ├── smoke/           ← 快速冒烟（无认证、有认证）
│   ├── apps/            ← 应用相关场景（含 workflow-run-publish.feature）
│   ├── auth/
│   └── step-definitions/
│       └── apps/
│           ├── workflow-run.steps.ts  ← 工作流运行验证步骤
│           ├── create-app.steps.ts
│           └── publish-app.steps.ts
├── support/
│   ├── api.ts           ← HTTP 数据准备（测试 fixture API）
│   └── world.ts         ← DifyWorld 共享状态对象
├── fixtures/
│   └── auth.ts          ← 预存认证状态（storageState）
└── scripts/
    └── run-cucumber.ts  ← 分级触发脚本（`e2e:full` vs 默认）
```

**关键模式 1 — API fixture 准备测试数据（support/api.ts）**:
```typescript
// 不走 UI，直接 POST 后端创建工作流 + sync DSL draft
export async function syncRunnableWorkflowDraft(appId: string): Promise<void> {
  const ctx = await createApiContext()  // 从 authStatePath 提取 cookie
  await ctx.post(`/console/api/apps/${appId}/workflows/draft`, {
    data: { graph: { nodes: [...minimal...], edges: [], viewport: {...} }, features: {} }
  })
}
```
本项目借鉴：api-client.ts 的 `apiFetch` 同角色，可直接 POST `/v1/workflows` + PUT `/v1/workflows/{id}/draft` 准备测试数据。

**关键模式 2 — DifyWorld 场景状态隔离**:
```typescript
class DifyWorld extends World {
  createdAppIds: string[] = []  // 每个 scenario 独立，afterEach 清理
  async startAuthenticatedSession(browser: Browser) {
    this.context = await browser.newContext({ storageState: authStatePath })
    this.page = await this.context.newPage()
  }
}
```
Playwright 原生 `test.beforeEach` + `page.context()` 等价，但 DifyWorld 在 Cucumber 中解决了 step 间共享状态问题。

**关键模式 3 — 工作流运行验证（workflow-run.steps.ts）**:
```typescript
When('I run the workflow', async function (this: DifyWorld) {
  await page.getByText('Test Run').click()
})
Then('the workflow run should succeed', async function (this: DifyWorld) {
  await page.getByText('DETAIL').click()
  await expect(page.getByText('SUCCESS').first()).toBeVisible({ timeout: 55_000 })
})
```
核心思路：触发运行 → 等待状态文本出现（长 timeout = 55s）。我们的 SSE 版本用事件流替代轮询，但等待模式一致。

**关键模式 4 — 测试分级（Cucumber tag）**:
- `@smoke` — 最轻量，CI 每次 PR 跑
- `@core` — 核心场景，每次合并跑
- `@mode-matrix` — 多 app 模式矩阵测试，按需触发

本项目等价：`RUN_E2E=1`（standard）/ `E2E_FULL_STACK=1`（full）环境变量分级，用 `test.skip()` 实现。

**关键模式 5 — Page Object 缺失（Dify 未用 POM）**:
Dify 的 step-definitions 直接操作 `page` 对象，未抽 Page Object Model。经验教训：当步骤共享的选择器增多时，变成维护负担。我们的 `canvas.page.ts` + `instance.page.ts` 抽象层是改进。

## 可借鉴的设计模式（具体文件路径 + 模式名 + 一句话说明）

| 文件 | 模式名 | 说明 |
|------|--------|------|
| `e2e/support/api.ts` | **API fixture 准备模式** | `createApiContext()` 从存储态提取 cookie，直接 HTTP 创建测试数据，比 UI 点击快 10x |
| `e2e/features/support/world.ts` | **World 状态隔离** | 每个 scenario 一个 World 实例，`createdAppIds[]` 跟踪副作用，afterAll 清理 |
| `e2e/features/step-definitions/apps/workflow-run.steps.ts` | **文本等待模式** | `getByText('SUCCESS').toBeVisible({ timeout: 55_000 })` 不轮询 DOM，等 React 渲染 |
| `e2e/cucumber.config.ts` | **分级触发配置** | profile 区分 smoke/full，对应我们的 `RUN_E2E` / `E2E_FULL_STACK` 环境变量 |
| `e2e/features/apps/workflow-run-publish.feature` | **Given/When/Then 场景结构** | 先 API 准备数据（Given via API），再 UI 触发（When），最后状态验证（Then） |

## 与本项目的关系（如何应用到 02-10）

### 1. API fixture 快速准备数据
`e2e/helpers/api-client.ts` 已有 `apiFetch`，02-10 的 spec 应先用 `apiFetch` 调：
- `POST /api/agent_builder/v1/workflows` 创建工作流
- `PUT /api/agent_builder/v1/workflows/{id}/draft` 保存 DSL（跳过 UI 拖拽，仅 canvas_drag spec 用 UI 拖）
- `POST /api/agent_builder/v1/workflows/{id}/publish` 发布

→ instance_run_realtime.spec.ts / instance_list_filter.spec.ts 均走 API fixture 建数据，不依赖画布 UI

### 2. SSE 验证不用 getByText — 用 EventSource
Dify 等 `getByText('SUCCESS')` 是 polling DOM，我们用 SSE 更直接：
```typescript
// instance.page.ts 中
async listenSseEvents(instanceId: string, timeout: number): Promise<SseEvent[]> {
  return page.evaluate(async ({ url, timeout }) => {
    return new Promise<SseEvent[]>((resolve) => {
      const es = new EventSource(url)
      const events: SseEvent[] = []
      es.onmessage = (e) => { events.push(JSON.parse(e.data)); ... }
      setTimeout(() => { es.close(); resolve(events) }, timeout)
    })
  }, { url: `${baseURL}/api/agent_builder/v1/instances/${instanceId}/events`, timeout })
}
```

### 3. 测试数据 DSL 由 dsl-builder.ts 提供
Dify 的 `syncMinimalWorkflowDraft` 内联了最小化 nodes/edges JSON。我们的 `dsl-builder.ts` 集中提供 4 种预设 DSL，复用于多个 spec，类似 Dify 的 `syncRunnableWorkflowDraft` 但更模块化。

### 4. 运行模式分级
Dify 用 Cucumber `--profile smoke/full` 分级。我们用 `process.env.RUN_E2E / E2E_FULL_STACK` + `test.skip()` 实现相同效果，无需额外配置文件，对 Playwright 生态更原生。

### 5. 避免重复 Dify 的 POM 缺失问题
Dify step-definitions 直接耦合选择器，维护难度高。我们统一在 `canvas.page.ts` / `instance.page.ts` 封装选择器，spec 层只调方法。
